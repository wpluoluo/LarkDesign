# 通用平面排版设计软件 · 完整技术可行性研究报告

> 融合 **Illustrator（矢量）+ Photoshop（位图/图层/滤镜）+ InDesign（排版/多页/印刷）**
> 内置 **Adobe 式云端 AI 中台**（推理模型操控全功能 + 生图模型 + 一键抠像/排版）
> 一套 ArkTS/ArkUI 代码，运行于 **HarmonyOS 手机/PC + OpenHarmony 设备/PC**
> 编制日期：2026-07-18

---

## 0. 关键结论（先行）

1. **技术可行性：成立。** 三类设计能力（矢量/位图/排版）均可由成熟 C/C++ 引擎在鸿蒙/开源鸿蒙 NDK 上落地，且全部**无 HMS 私有依赖**，满足"一套代码双发行版"硬约束。
2. **"AI 全用云端"是正确决策。** 它把最重的工程风险（端侧推理移植、双发行版 AI 分流、NPU 适配）整体移除。本地仅剩"渲染 + 排版 + 导出"三块引擎，复杂度下降一个量级。
3. **生图/编辑模型已可商用。** 通义万相 Qwen Image 2.0（2K、中文文字渲染业界最佳、支持图生图编辑）+ 即梦 Seedream 已构成"生图 + 一键抠像/改图"的云端闭环，无需自研模型。
4. **AI 中台是"模型无关"协议层，而非厂商锁定。** 中台定义一套标准集成协议（以 OpenAI 兼容 Chat/tool_use 协议为事实标准），任何满足协议的大模型都能即插即用（BYOK：用户填 endpoint+key）。DeepSeek/Qwen/GLM 等只是"默认 recipe"，非绑定。Function Calling 调度本地引擎是已被验证的范式。
5. **最大工程门槛只剩两处**：① Skia 在 NDK 的编译 + NAPI 桥接（有完整先例）；② 融合文档模型（DOM）的设计——这是产品的真正技术护城河，需自研。
6. **文件格式双轨制已定**：① 开源/开放格式优先——SVG、ODG（ODF/ISO 26300）、PDF 2.0（含 PDF/X-4 印刷、PDF/A-4 归档、PDF/UA-2 无障碍）、OpenRaster（.ora）、PNG/WebP/AVIF/TIFF/OpenEXR、OpenType/WOFF2 字体等，保证互操作、不被锁死；② 专用原生格式 `.hds`（ZIP 容器 + 结构化清单）承载 Fusion DOM 全量信息（矢量+位图+多页+印刷+**AI 上下文/可复现**+版本历史），规范公开以保证长期可恢复。详见第 9 章。
7. **产品化闭环已补齐**：MCP 负责外部 Agent 协议，CLI 负责脚本/CI 执行，Skill 负责能力编排，会员/Entitlement 负责个人、团队和企业授权；四者统一复用 Command Registry、Job、Permission、Audit，避免接口漂移与重复实现。详见第 12、13 章。

## 2. 融合文档模型（Fusion DOM）—— 核心技术护城河

### 2.1 设计原则
三类软件的本质差异在于**对象模型**：Illustrator 是"路径树"，Photoshop 是"像素图层栈"，InDesign 是"多页文本流"。融合的关键是建立**一个能同时容纳矢量对象与像素图层的统一场景图（Scene Graph）**，并以"图层"为统一容器。

> 参考范式：**Affinity Designer/Photo/Publisher** 共用同一文档模型（矢量 Persona + 像素 Persona 切換）；**Krita** 的 `KisImage = 像素数据 + 图层层级`，支持 7 类图层、76 种混合模式、非破坏性编辑。本产品取其"统一图层容器 + 多对象类型"思想，叠加 InDesign 的多页结构。

### 2.2 对象层级（伪结构）

```
Document
 ├─ Pages[]                         // InDesign 多页
 │   ├─ MasterPage (可选主页)        // 页眉/页码/网格
 │   └─ Page
 │       ├─ LayerStack[]            // Photoshop 图层栈（从底到顶）
 │       │   ├─ VectorLayer         // 矢量：路径/形状/文本/图像占位
 │       │   │   └─ Objects[]: Path | Shape | TextFrame | Group
 │       │   ├─ RasterLayer         // 位图：像素缓冲 + alpha
 │       │   │   └─ PixelBuffer (Skia Surface)
 │       │   ├─ AdjustmentLayer     // 调整层：色阶/曲线/色相
 │       │   ├─ MaskLayer           // 蒙版
 │       │   ├─ FilterLayer         // 滤镜（非破坏性）
 │       │   └─ GroupLayer
 │       └─ PageStyle (尺寸/出血/边距)
 ├─ TextStyles[]                    // 字符/段落样式（InDesign）
 ├─ Assets[]                        // 字体/笔刷/渐变/色板
 └─ Metadata
```

### 2.3 关键设计决策
- **图层是统一容器**：矢量层与像素层平级，渲染时统一走 Skia 合成。
- **文本是矢量对象**：文本框架（TextFrame）既是 InDesign 的排版单元，也是 Illustrator 的文字对象，共享 FreeType/HarfBuzz 整形。
- **每个对象可序列化**：文档存为自有格式（类 `.kra`/`.afdesign` 的 JSON+二进制），导出 SVG/PDF/PNG。
- **AI 操作 = 一等文档操作**：每次 AI 动作（抠像/生图/排版）最终都落为"新增图层/修改对象/套用样式"，与手动操作同构——这是 AI 中台能"操控所有功能"的底层前提。

### 2.4 渲染管线
```
对象树 → Skia DisplayList → (CPU 光栅化 | GPU/Vulkan/Metal) → 合成帧 → 屏幕 / 导出
```
- 矢量路径、文本整形、位图混合、滤镜全部经 Skia 统一管线。
- 复杂文档用 Skia 的 **Picture/DisplayList** 缓存已绘制指令，避免重复光栅化（规避 Inkscape/Cairo 在百万节点下的 CPU 瓶颈）。

## 3. 云端 AI 中台架构

### 3.1 核心原则：协议而非厂商（关键架构约束）

> **用户明确约束**：云端模型不是"锁定几家具体厂商"，而是**一套系统集成协议**——任何支持该协议的大模型都能即插即用。

中台不内置对某一家的依赖。它定义一套**标准集成协议**（请求/响应/能力声明格式 + 工具调用契约），任何满足协议的后端模型，经"用户配置 endpoint + API Key"（BYOK）即可接入。这带来两个直接收益：
1. **架构解耦**：应用层与"此刻用哪家模型"彻底分离，换模型 = 换配置，不碰代码。
2. **产品特性**：本软件天然成为"模型无关的 AI 设计 Agent"——用户用自己的模型额度（DeepSeek/Qwen/GLM/豆包/Kimi/自托管…），应用不绑定、不转售、不分润，信任成本最低。

### 3.2 协议标准选型（事实标准，非自创）

| 能力面 | 采用的协议基线 | 说明 |
|---|---|---|
| 文本推理 / 对话 | **OpenAI 兼容 Chat Completions** | 事实标准；国内几乎所有模型（DeepSeek/Qwen/GLM/豆包Ark/MiniMax/阶跃/百川/Kimi…）均提供兼容 endpoint |
| 工具调用 | **OpenAI function calling / tool_use schema** | 事实标准；同上一并兼容 |
| 多模态视觉输入 | **OpenAI `content[].image_url` 视觉消息格式** | Qwen-VL/GLM-4V/豆包视觉等支持；画布截图按此格式传入 |
| 文生图 | **OpenAI `images.generate` 格式为参考基线**（prompt/size/response_format）+ `image_edit`/`image_variation` 扩展 | 各厂商镜像此格式；不足处用扩展字段补齐 |
| 协议可插拔 | **`ProtocolDriver` 抽象接口** | 除 OpenAI 兼容外，未来可加 Anthropic Messages / Google Gemini / 私有协议（如你的 `juece.cloud` 网关协议） |

> 不重复造协议轮子：以 OpenAI 兼容为"最小公分母"基线，是因为它已是国内模型生态的事实接入标准，可零改造接入最多后端。协议驱动层（`ProtocolDriver`）保证未来可侧向其它标准而不动业务。

### 3.3 分层架构（协议层视角）

```
┌──────────────────────────────────────────────────────────────┐
│  ArkTS UI 层（画布 / 指令栏 / 属性面板）                        │
├──────────────────────────────────────────────────────────────┤
│  AI 中台调度层（本地，ArkTS）                                   │
│   · 功能函数注册中心（每个能力 = 一个 tool）                      │
│   · 上下文装配（文档状态 + 工具 Schema + 画布缩略图）              │
│   · 能力需求声明（如：需要 vision + tool_use）                    │
├──────────────────────────────────────────────────────────────┤
│  【模型集成协议层 · Model Integration Protocol Layer】            │
│   · Capability Registry（模型能力注册表）                         │
│   · ModelRouter（按策略选模型：成本/质量/延迟/用户偏好）           │
│   · ProtocolDriver（OpenAI兼容 / Anthropic / 私有 … 可插拔）      │
│   · BYOK 配置（endpoint + key，用户自填，零厂商锁定）              │
├──────────────────────────────────────────────────────────────┤
│  任意后端（用户配置的模型，满足协议即可）                          │
│   推理类 endpoint · 视觉类 endpoint · 生图类 endpoint · 自托管网关  │
├──────────────────────────────────────────────────────────────┤
│  本地引擎层（C/C++ via NAPI）                                    │
│  Skia（渲染） FreeType/HarfBuzz/ICU（排版）                      │
│  libHaru/PDFium（导出） OpenCV（可选图像处理）                    │
└──────────────────────────────────────────────────────────────┘
```

### 3.4 能力注册表 + 路由（模型无关的核心机制）

- **Capability Registry（能力注册表）**：每个接入的模型声明能力标签——`text` / `vision` / `tool_use` / `image_gen` / `image_edit`，并附上下文窗、价格权重、延迟档位。
- **ModelRouter（路由）**：收到带"所需能力"的请求后，按当前策略（用户偏好 / 成本优先 / 质量优先 / 延迟优先）从已注册模型中选择最合适的 endpoint。
- **示例**：用户指令"把这张海报调得更平衡"+ 画布截图 → 需求 `vision + text + tool_use` → 路由到用户已配置且具备该能力的模型（可能是 Qwen-VL、GLM-4V、豆包视觉等任意一个），中台代码不感知具体厂商。
- **默认 recipe（非锁定）**：出厂预置若干"开箱即用"的协议配方（见 3.5），用户可删可换，核心是协议而非具体模型。

### 3.5 默认接入配方（仅作参考实现，可删可换）

| 能力 | 可作默认 recipe 的模型（示例） | 说明 |
|---|---|---|
| 文本推理 / 调度 | DeepSeek / Qwen / GLM / Kimi / 豆包 | 均 OpenAI 兼容，BYOK 即接 |
| 视觉理解（看画布） | Qwen-VL / GLM-4V / 豆包视觉 | 接收画布截图做视觉指令 |
| 文生图 | 通义万相 / 即梦 / 智谱 CogView / 可灵 | 走 images.generate 兼容格式 |
| 图生图编辑 / 一键抠像 | 通义万相 Edit / 即梦 Edit / Wanx Edit | 走 image_edit 扩展，返回带 alpha PNG |

> 以上**全部只是默认配置样例**。用户删掉任一、换成自家网关或任意兼容模型，中台行为完全一致——这是"协议层"架构的根本意义。

### 3.6 自托管网关（可选，进一步解耦）

你已有的 `juece.cloud` 服务器与 OpenClaw 网关，可实现一个**协议兼容聚合层**：把多个后端模型聚合成一个 OpenAI 兼容 endpoint，对外只暴露一个地址。这样中台只需对接一个稳定协议接口，后端模型轮换/灰度/降级全在网关侧完成，应用零改动。

### 3.7 Function Calling 调度范式（AI 操控全功能，不变）

1. **注册工具集**：`generateImage(prompt,size,style)`、`removeBg(imageRef)`、`addText(content,font,style)`、`createVectorPath(points)`、`applyStyle(template)`、`autoLayout(preset)`、`exportPDF(preset)`……
2. **上下文装配**：把当前文档状态（图层清单、选中对象、可用样式）+ 工具 Schema +（必要时）画布截图，拼成符合协议的请求。
3. **模型决策**：经 ModelRouter 选中的模型把"把这张图背景去掉，生成一句 slogan 排成海报"拆成 `removeBg() → generateText() → autoLayout()` 的调用序列（工具调用契约，与厂商无关）。
4. **执行回流**：每个 tool 映射到本地引擎操作，结果作为图层/对象变更实时回流 Skia 画布。

## 4. 本地引擎层与可移植库

### 4.1 渲染引擎：Skia（唯一推荐）

| 项 | 结论 |
|---|---|
| 地位 | Google 2D 引擎，Chrome/Flutter/Android 同款；**OpenHarmony 图形栈 Rosen 本身基于 Skia** |
| 矢量+位图+文本+滤镜 | 全支持，统一 DisplayList 管线，GPU 后端（Vulkan/GL） |
| 鸿蒙移植 | ✅ 已验证：用 OHOS NDK toolchain + gn 参数 `is_ohos / ohos_ndk` 编译出 `libskia.a`；经 NAPI + XComponent 画布对接 ArkUI |
| 双发行版 | ✅ 同一套 C++ 代码编译为 HarmonyOS / OpenHarmony 两个 .so，业务层零差异 |
| SVG / PDF | Skia 内置 `skia_enable_svg / skia_enable_pdf`，可直接导入 SVG、导出 PDF |

**为什么不自己造渲染器**：矢量贝塞尔 + 位图混合 + 文本整形 + 滤镜 + 色彩管理，是自研成本极高的领域。Skia 是工业级答案，且鸿蒙官方图形栈本就源于它——兼容性最佳。

**为什么不纯用 ArkUI Canvas**：ArkUI Canvas 在"数千个独立矢量元素"场景下，每个路径都是一次 UI 组件更新，性能崩塌；Skia 把所有绘制转成指令一次性提交 GPU。专业设计软件必须用 Skia。

### 4.2 排版系统：FreeType / HarfBuzz / ICU（系统级零成本）

| 库 | 作用 | 鸿蒙状态 |
|---|---|---|
| **FreeType** | 矢量字体光栅化 | OpenHarmony `graphic_ui` 直接依赖，**系统内置**，无需移植 |
| **HarfBuzz** | 复杂文本整形（CJK/阿拉伯文/连字） | 系统可选内置 |
| **ICU** | 换行/分词（含 `line_cj.brk` 中文规则） | 系统内置 |

> 这是"印刷平面"模块的地基——别人要造轮子，你直接获得专业级文字排版能力。中文排版（禁则/标点挤压/竖排）可由 ICU 规则 + 自有排版引擎补全。

### 4.3 PDF / 印刷导出

| 库 | 作用 | 鸿蒙状态 |
|---|---|---|
| **libHaru v2.4.4** | C 语言生成 PDF，轻量，依赖仅 zlib+libpng | ✅ 已在 HarmonyOS 6.1.0（PC）验证通过，NAPI 桥接 4 接口 |
| **PDFium** | PDF 渲染/导入 | ✅ `linux-musl-arm64` 预编译版与 HarmonyOS musl libc 兼容，可直接用 |
| **LittleCMS** | 色彩空间转换（RGB↔CMYK） | 需移植，C 语言，难度低 |

**印刷（CMYK）诚实评估**：
- 普通 RGB PDF 导出（屏幕/数码打样/电商）用 libHaru 即可，Phase 1 即可交付。
- **专业印刷 CMYK 输出**不是 libHaru 的强项——需引入 LittleCMS 做色彩转换 + 自写 CMYK PDF 对象，或 Phase 2/3 通过云端/桌面协同生成。建议把"CMYK 专业印刷"列为 Phase 3 增强，不阻塞首版。

### 4.4 图像处理（可选）：OpenCV
- 端侧抠像/滤镜的精细 refinement、基础图像算子可用 `opencv-mobile`（已移植鸿蒙）。
- **非必需**——核心抠像/编辑已走云端模型。本地 OpenCV 仅作"离线兜底 + 实时交互"增强。

## 5. 双发行版 / 双形态工程策略

### 5.1 构建架构（沿用既定方案）
- 项目级 `build-profile.json5`：两个 product——`harmonyPhone`（runtimeOS=HarmonyOS，bundleType=app）、`openharmonyDevice`（runtimeOS=OpenHarmony）。
- 模块级多 target：`default`（双平台共用）、`harmonyOnly`、`ohosOnly`。
- AI 协议、Fusion Core、渲染/排版/导出核心放入共享模块或 `default` target；HarmonyOS/OpenHarmony 的网络、安全存储、文件、输入和窗口能力由平台 adapter 注入，并通过 capability matrix 验证差异。

### 5.2 形态适配
| 形态 | 主控交互 | 说明 |
|---|---|---|
| 手机 | 查看/轻改/AI 指令 | 触屏 + 语音唤起 AI 中台 |
| 平板（MatePad） | 手写笔绘制矢量/位图 | 压感笔事件 → Skia 笔迹 |
| PC（MateBook / 开源鸿蒙 PC） | 精准键鼠 + 大屏多面板 | 主生产力形态，钢笔/节点编辑/多页排版 |

### 5.3 云端依赖的双发行版一致性
- AI 中台与本地引擎**均不区分发行版**——云端 API 是标准 HTTPS 调用，Skia/FreeType/PDF 库双平台同源码。这是"一套代码"约束被干净满足的关键。

## 6. 分期落地路线（控制风险）

## 9. 文件格式规范（双轨制：开源优先 + 专用原生）

文件格式是"不被平台/厂商锁死"这一产品哲学的落地支点。采用**双轨制**：

- **轨 A · 开源/开放格式（优先支持，导入/导出）**：保证与整个设计生态互操作，用户随时可带着文件离开。
- **轨 B · 专用原生格式（`.hds`，全量承载）**：承载 Fusion DOM 的全部信息——尤其是开放格式表达不了的 **AI 可复现上下文**与**版本历史**。规范公开发布，容器用开放 ZIP，即便本应用停止维护，文件仍可解包恢复。

**设计要点**
- **P0 是 MVP 必交付**：SVG、PNG、WebP、JPEG、PDF 2.0、PDF/X-4、OpenType、ODG。这 8 个覆盖 90% 的真实交换场景。
- **Adobe 私有格式（AI/PSD/IDML）只做"导入兼容"，不做导出**——既降低用户从 Adobe 迁移的门槛，又坚守"开源优先、不反锁"的立场。
- **SVG + ODG + EPS 是"开放矢量"三锚点**：SVG 是 Web/现代矢量标准，ODG 是开源矢量文档，EPS 是印刷/标志/雕刻圈的事实交换格式——三者覆盖从屏幕到印前的全链路矢量互操作，构成对 Adobe AI 的开放替代交换链。OpenRaster 则作为"开源版 .psd"的位图分层锚点。
- **EPS 的特殊性（务必正视）**：EPS 本质是一段 **PostScript 文本程序**（带 DSC 头注释），不是二进制容器。这带来一个非对称难度——

**EPS 导入/导出技术评估**

| 方向 | 难度 | 实现路径 | 工作量估计 |
|---|---|---|---|
| **导出（写 EPS）** | 低 | 生成 DSC 合规矢量子集：路径构造算子（`m`/`l`/`c`/`v`/`y`/`re`）+ 填充/描边（`f`/`s`/`S`/`B`）+ 颜色（`rg`/`k`）+ 文本（`show`，引用嵌入字体）+ `%%BoundingBox` 头 | 1–2 周（基础矢量子集）；满足 90% 标志/插画导出 |
| **导入（读 EPS，纯矢量标志）** | 中 | 轻量路径提取器：解析 PostScript token 流，拦截路径构造/绘制/颜色算子，重建矢量路径树（不解释算术/循环/光栅嵌入） | 2–3 周；覆盖"纯矢量 logo"常见情况 |
| **导入（全保真）** | 高 | 集成 **Ghostscript**（C，~30MB，NDK 交叉编译；Android 已有移植先例，鸿蒙 NDK 可行）；渲染为高分辨率位图或经 gs 矢量提取 | 移植+集成 3–4 周；处理含算术/RIP 逻辑的复杂 EPS |

> **决策建议**：MVP 先交付 **EPS 导出（P1）+ 轻量矢量路径导入（P1）**，覆盖标志/插画互换主场景；**Ghostscript 全保真导入列为 P2**，待用户量起来后按需求补。注意 EPS 与 PDF 的关系——现代印前正从 EPS 迁向 PDF/X-4，但雕刻机/老 RIP/广告公司仍收 EPS，故**两者并行支持**（PDF/X-4 为现代出口、EPS 为兼容出口）方能通吃新旧印前链路。

### 9.2 轨 B：专用原生格式 `.hds`（Harmony Design Studio）

> 承载 Fusion DOM 的**全量**信息。开放格式只能表达"渲染结果或单层结构"，而 `.hds` 要表达"可继续编辑、可 AI 复现、可回溯"的完整工程态。

**容器（沿用开放生态成熟范式）**

```
xxx.hds                         ← ZIP 包（同 .docx/.odg/.ora 哲学：换后缀即可解包）
├ mimetype                      ← 首文件，STORED 不压缩，内容：application/x-harmony-design
├ manifest.json                 ← 文档元数据：版本号、创建工具、Fusion DOM 根引用、能力声明
├ document.json                 ← ★ Fusion DOM 序列化：pages[] → objects[](vector/raster/text/group/
│                                  adjustment/mask/smart) → 属性/变换/样式引用
├ assets/                       ← 位图图层原图(PNG/WebP)、嵌入字体(TTF/OTF/WOFF2)、外部图片引用
├ styles/                       ← 字符样式库、段落样式库、色板(swatch)、符号(symbol)、画笔
├ print/                        ← 印刷预设：CMYK 配置、专色、出血/裁切、拼版(imposition)、输出意图
├ ai/                           ← ★ AI 上下文：每条生成记录的 prompt + 模型 recipe(协议endpoint/版本) +
│                                  参数(seed/尺寸/风格) + 输入引用 + 时间戳 → 支持"重新生成/局部重做"
├ thumbnails/thumbnail.png      ← 预览图（文件管理器快速渲染）
├ history/                      ← 命令日志(undo/redo)，类 PSD/ORA 提案；支持分支/时间点回溯
└ meta.xml                      ← Dublin Core 元数据（作者/创建时间/版权/XMP）
```

**为什么这样设计（对应你的硬约束）**

| 要求 | 设计回应 |
|---|---|
| 全量承载 Fusion DOM | `document.json` 序列化统一场景图（矢量+像素+多页+文本流），开放格式做不到 |
| **AI 可复现**（你的核心诉求） | `ai/` 目录存"prompt + 模型 recipe + 参数 + 输入引用"，AI 生成的对象可被**重新生成或局部重做**，而非死像素 |
| 不被锁死 / 长期可恢复 | ZIP 容器 + 公开规范 + `mimetype` 魔术字节；应用停更也能解包取回资源 |
| 大文档性能 | `assets/` 资源外置、按需懒加载；`document.json` 只存结构，像素不内联 |
| 版本/协作 | `history/` 命令日志天然支持 undo/redo；可作为后续多人协作的操作同步基础 |
| 自包含可移植 | 字体/图片内嵌 `assets/`，单文件带走整个工程 |
| 前后向兼容 | `manifest.json` 带 `version` 字段；未知扩展走独立命名空间，不破坏基线解析 |
| 双发行版零差异 | `.hds` 是纯数据格式，与 HarmonyOS/OpenHarmony 运行时无关，一套文件两端通读 |

**`.hds` 与开放格式的转换关系**

```
           导入                          .hds (编辑态, 全量)
  SVG/ODG/EPS/AI ───►  解析为 Fusion DOM  ──────►  保存为 .hds
  PNG/WebP/PSD ──────►  落为 RasterLayer
  IDML ──────────►  映射为 pages + 文本流 + 样式
           导出
  .hds ──► SVG·EPS·ODG (矢量) / PNG·WebP·TIFF (位图) / PDF 2.0·X-4·A-4 (出版)
  .hds ──► OpenRaster (开源分层交换)
```

**规范公开策略**：`.hds` 容器结构与 `document.json` 的字段定义将作为**开放规范**随首版发布（独立文档 `format-spec.md`），允许第三方读写器实现。这既是对"开源优先"立场的兑现，也是建立生态信任、防止自身被质疑"换成另一种私有锁"的关键。

## 10. 全功能模块架构研究（融合 Illustrator + Photoshop + InDesign）

把"三合一"能力按模块拆开，逐个确认：**① 功能范围 ② 鸿蒙原生落地（HarmonyOS/OpenHarmony 双发行版）③ Fusion DOM 映射 ④ AI 中台可操控性**。

### 10.1 色彩管理 (Color Management)

- **功能范围**：色彩空间（sRGB / Display P3 / Adobe RGB / ProPhoto / CIE Lab / XYZ / CMYK）、ICC profile 加载与转换、专色（Pantone 等命名色）、渐变（线性/径向/锥形/网格）、色板、色彩和谐、软打样、色域警告、黑点补偿。
- **鸿蒙落地**：引擎用 **LittleCMS 2（lcms2）**——MIT 许可、C99、完整 ICC 4.4 实现；**鸿蒙 PC 移植实践已证实**（pngquant 移植经 Lycium++/vcpkg-ohos 交叉编译已用 lcms2）。支持多至 15 色油墨、黑点补偿、软打样、色域检查。**无 HMS 依赖，双发行版零差异**。
- **Fusion DOM 映射**：每个颜色对象存 `(space, values[], profileRef?)`；渐变存 `stops[]`（每 stop 一个颜色）；专色存 `namedColor` 引用。
- **AI 操控**：`setColor(obj, space, values)` / `convertSpace(doc, 'CMYK')` / `createGradient(...)`。例："把主色调暖 10%" → 改 Lab a* 通道。

### 10.2 字体管理 (Font Management)

- **功能范围**：字体注册/激活/嵌入、字体回退链（**CJK 关键**）、OpenType 特性（连字/小型大写/花体/序数）、可变字体轴控、字偶距/字距/行距/基线网格、字体配对推荐。
- **鸿蒙落地**：光栅化 **FreeType**（系统内置）、整形 **HarfBuzz**（系统可选内置）；HarmonyOS 提供 `OH_Drawing_CreateSharedFontCollection` / `OH_Drawing_SetTextStyleFontFamilies` / 字体 fallback group / `DisableFontCollectionSystemFont` 原生 API。**关键坑（已核实）**：OpenHarmony **不自动回退**——开发者须显式实现回退链（自定义字体缺字 → 系统字体 → sans-serif），否则生僻字变方框。字体管理层必须**自建**，非系统白给。
- **Fusion DOM 映射**：文本对象存 `fontRef(embedded or familyName) + features[] + variableAxes{} + tracking/leading`。
- **AI 操控**：`setFont(textObj, family, {weight, axis})` / `enableOTFeature(textObj, 'smcp')` / `autoPairHeading()` / `fixCJKFallback()`。

### 10.3 图层管理 (Layer Management)

- **功能范围**：图层树（嵌套组）、图层类型（矢量/像素/文本/调整/蒙版/智能对象/符号实例）、混合模式（约 27 种）、不透明度、剪贴蒙版、图层复合、锁定/可见、非破坏性调整、图层效果（投影/发光/斜面）。
- **鸿蒙落地**：混合模式由 **Skia**（Porter-Duff + 高级混合）实现；图层树是 Fusion DOM 对象容器（纯 ArkTS）。智能对象/非破坏调整 = **节点图（node graph）**，渲染时求值。
- **Fusion DOM 映射**：每个对象含 `blendMode / opacity / clipMask / effects[] / locked / visible`。
- **AI 操控**：`group(sel)` / `setBlendMode(layer,'multiply')` / `addEffect(layer,'dropShadow',{...})` / `applyAdjustment(layer,'levels',{...})`。

### 10.4 工具管理 (Tool Management)

- **功能范围**：工具注册表（插件化）、选择/移动/变换、钢笔/贝塞尔、形状、文本、笔刷/绘画、橡皮、渐变、吸管、切片、测量、协作光标。
- **鸿蒙落地**：工具是 **Command 模式**插件——注册 `(id, icon, pointerHandlers, modifierHandlers)`；ArkUI 手势/鼠标事件分发到当前工具。PC 端键鼠精确、移动端触摸、平板笔绘经**输入抽象层**归一。
- **Fusion DOM 映射**：工具本身不入库（运行时）；工具产生的操作落为命令 → 对象变更。
- **AI 操控（关键）**：AI 不"用工具"，而是直接调用工具背后的**功能函数**——`drawPen(points)` / `addText(...)` / `applyGradient(...)`。**工具与 AI 共用同一命令层**，这是"AI 操控所有功能"的落地支点。

### 10.5 板式/排版管理 (Layout & Typography — InDesign 域)

- **功能范围**：页面 + 主页（母版）、文本框 + 文本串流（跨框续排）、栏/分栏、基线网格、字符/段落样式、连字与两端对齐（ICU 断行）、表、脚注、目录、索引、液态排版、交互 PDF（超链接/按钮）。
- **鸿蒙落地**：文本整形 HarfBuzz + 断行 **ICU**（系统内置，含 `line_cj.brk` 中文规则）；排版模型是 Fusion DOM 的 `pages[] + textFrames[] + styles[]`。**这是当前鸿蒙生态完全空白的域**（华为不做垂直排版），差异化核心。
- **Fusion DOM 映射**：`page` 含 `masterRef / margins / columns / frames[]`；`textFrame` 含 `content + linkedFrame + styleRefs`；`paragraphStyle/characterStyle` 库。
- **AI 操控**：`createMasterPage(...)` / `threadText(frameA,frameB)` / `applyParagraphStyle(...)` / `autoBalanceColumns()` / `generateTOC()`。例："把这页排成杂志风，左文右图" → 应用主页 + 串流 + 样式。

### 10.6 尺寸/画布管理 (Document & Dimension)

- **功能范围**：画板（Illustrator 多 artboard）/ 页面（InDesign 多页）、DPI/PPI、单位（px/pt/mm/cm/inch/pica）、标尺/参考线/网格/吸附、出血/裁切线（印刷）、边距、响应式画布（移动 vs PC 不同 UI 密度但同文档模型）。
- **鸿蒙落地**：纯数据 + ArkUI 渲染；出血/裁切在导出 PDF/X-4 时由印刷模块处理。**UI 分层、文档模型统一**——移动端单画板聚焦 + 手势缩放，PC 端多画板/多页总览 + 精确数值输入。
- **Fusion DOM 映射**：`document` 含 `units / dpi / artboards[]或pages[]`，每画板含 `size / bleed / margin / guides[]`。
- **AI 操控**：`setDocumentSize(...)` / `addArtboard(...)` / `setBleed(...)` / `switchUnit('mm')`。

### 10.7 其余模块（简述）

- **矢量编辑**：路径/锚点/控制柄、布尔运算（合集/差集/交集/排除）、描边（端点/连接/虚线）、填充（纯色/渐变/图案）、形状生成器。Skia `SkPath` 提供完整路径 API。
- **位图编辑**：像素笔刷、调整（色阶/曲线/色相饱和度/曝光）、修复/仿制、液化、智能滤镜（非破坏）。像素缓冲用 Skia `SkBitmap`/GPU 纹理；调整层走节点图。
- **蒙版**：图层蒙版（alpha）、剪贴蒙版、矢量蒙版、亮度蒙版——DOM 中 `mask` 字段引用灰度/矢量对象。
- **变换**：移动/缩放/旋转/斜切/自由变换、对齐/分布、微移——所有对象共享 `transform` 矩阵，Skia 渲染时应用。
- **效果/滤镜**：模糊/锐化/噪点/扭曲/风格化、实时效果（节点图求值）。P1，先实现 5–8 个高频。
- **资源/素材库**：符号、样式、色板、画笔、模板、库（类 Adobe Libraries）——存于 `styles/` 与用户库，跨文档复用。
- **历史/撤销**：命令模式栈 + 分支快照（对应 `.hds` 的 `history/`），支持时间点回溯。
- **印前/打印**：分色预览、陷印、叠印、拼版、PDF/X-4 输出——Phase 4。
- **无障碍**：标签 PDF、替代文本、阅读顺序（PDF/UA-2）——Phase 4。
- **协作**：在线状态、批注、CRDT 同步——Phase 6（多端实时，正好吃鸿蒙分布式软总线特性）。

### 10.8 双发行版 × 双形态 一致性矩阵

| 模块 | 实现层 | HarmonyOS | OpenHarmony | 形态差异（PC vs 移动） |
|---|---|---|---|---|
| 色彩 | lcms2 (NAPI) | ✅ | ✅ 同库 | 无 |
| 字体 | FreeType+HarfBuzz (系统) | ✅ | ✅ 同 | 回退链须自建（OH 不自动） |
| 图层/矢量/位图 | Skia (NAPI) | ✅ | ✅ 同（Rosen 本就基于 Skia） | 无（渲染一致） |
| 排版 | HarfBuzz+ICU (系统) | ✅ | ✅ 同 | 无 |
| 工具/命令/样式/变换/DOM | ArkTS Feature + 平台无关契约/Fusion Core | ✅ | ✅ 共享核心 | **UI 分层**（PC 精确输入/多页总览，移动单画板/手势） |
| 历史/资源/AI 中台 | Command/Job 契约 + ArkTS adapter + HTTPS | ✅ | ✅ 共享协议 | 网络、安全存储和后台能力按平台适配 |

> 结论：核心数据、Command schema 和 Fusion Core 应共享；NAPI/系统 API、字体回退、文件授权、输入、窗口和分发通过 Platform Port 适配。业务规则保持单一来源，但平台实现允许受控差异。

### 10.9 AI 中台可操控性分级

| 等级 | 类型 | 说明 | 示例 |
|---|---|---|---|
| **L1 直接参数** | AI 改属性 | 函数直接设值，无需生成 | 改色彩/字体/混合/变换/尺寸 |
| **L2 生成对象** | AI 产出对象 | 调云端模型 + 落图层 | 矢量生成/生图/排版样式 |
| **L3 编排序列** | AI 多步 | LLM 拆函数调用链 | "做成杂志风" → 主页+串流+样式 |
| **L4 视觉感知** | 需看懂画布 | 多模态模型 + 画布截图 | "把这海报调平衡""字号太大" |

> 所有等级共享同一**功能函数注册中心**（第 3 章 AI 中台）：工具、菜单、AI 指令三者同源。这是"AI 操控软件所有功能"的工程本质。

## 11. 交互与体验规划（快捷键 / UI 显示 / 可用性）

> 本章基于 2026-07-18 核查的鸿蒙官方事实：ArkUI 断点体系（xs/sm/md/lg/xl 横向 + sm/md/lg 纵向，4/8/12 栅格，8vp 网格，vp/fp 单位）、`@ohos.multimodalInput.inputConsumer` 全局快捷键 API（API 14+，preKeys 最多 2 修饰键）、系统保留快捷键清单、Figma 国际化快捷键工程经验。

### 11.1 快捷键规划：四模态输入 + 协议化注册

设计软件的核心生产力来自**高频操作的零摩擦触发**。本产品的输入不是单一键鼠，而是**四模态并存**，且全部映射到同一套**功能函数注册中心**（第 3 章 AI 中台）——这正是"键盘快捷键、触控手势、手写笔、AI 自然语言指令"四种输入能统一操控软件所有功能的工程基础。

#### 11.1.1 输入模态矩阵

| 模态 | 主形态 | 触发方式 | 对应功能层 | 双发行版一致性 |
|---|---|---|---|---|
| **物理键鼠** | PC（HarmonyOS/OH PC） | 输入 Port + 平台快捷键 adapter | 全功能快捷键 | 共享映射，平台注册能力适配 |
| **触控手势** | 手机/平板/折叠 | ArkUI `Gesture` adapter | 视图变换/工具/径向菜单 | 共享命令，手势能力适配 |
| **手写笔** | 平板（MatePad 笔） | Pen Input Port（压感/倾斜/按键） | 绘制/擦除/选择 | 设备能力矩阵与降级 |
| **语音 + AI 指令** | 全形态 | AI 命令面板；系统语音入口可选 | 自然语言 → Function Calling | AI 协议共享，系统入口适配 |

**关键认知**：四模态最终都落到同一组命令（Command），与 AI 中台共享注册中心。用户用快捷键、用手势、用语音说"把这图背景去掉"，执行的是**同一个 `removeBg()` 命令**。这是产品一致性的根基，也是"AI 操控所有功能"在交互层的兑现。

#### 11.1.2 系统保留快捷键避让表（必须查，否则冲突报错 4200002）

鸿蒙系统已占用一批快捷键，**应用不可重复注册**，否则 `inputConsumer.on('hotkeyChange')` 返回 `4200002 The hotkey has been used by the system`。已确认的保留键：

| 组合 | 系统行为 | 备注 |
|---|---|---|
| 鸿蒙键（单按） | 开始菜单 | 电脑模式生效 |
| 鸿蒙键 + ? | 系统快捷键提示面板 | **可借鉴做应用内快捷键帮助** |
| 鸿蒙键 + ← / → | 左/右分屏 | 窗口管理 |
| 鸿蒙键 + ↑ / M / ↓ | 最大化 / 最小化 | 窗口管理 |
| 鸿蒙键 + A | 应用中心 | 电脑模式 |
| 鸿蒙键 + 返回 | 返回上一步 | 类系统返回 |
| 鸿蒙键 + 空格 / Ctrl+Shift | 切换输入法 | — |
| Ctrl + Shift + Esc | 任务管理器 | 电脑模式 |
| Ctrl + Alt + Del | 安全窗口 | 电脑模式 |
| 智慧键（单按/长按） | 小艺对话/语音 | 可 Hook 唤起本产品 AI 面板 |
| 音量键（前台时） | 可优先响应拦截 | `keyPressed` 订阅，用于画布缩放/翻页 |

**策略**：产品快捷键**避开鸿蒙键组合**（留给系统），主用 `Ctrl/Shift/Alt + 字母/功能键`。智慧键作为"唤起 AI 中台"的黄金入口（类比小艺，但指向本产品的命令面板）。

#### 11.1.3 快捷键体系架构（协议化、可配置、国际化）

复用第 3 章的协议思想，快捷键定义为**数据而非硬编码**：

```
shortcuts.json
├─ context: global | canvas | textEdit | dialog   # 模态上下文
├─ bindings:
│   { "action":"tool.select",      "win":"V",        "mac":"V" }
│   { "action":"tool.pen",         "win":"P" }
│   { "action":"transform",        "win":"Ctrl+T" }
│   { "action":"duplicate",        "win":"Ctrl+D",   "mac":"Cmd+D" }
│   { "action":"group",            "win":"Ctrl+G" }
│   { "action":"ai.commandPalette","win":"Ctrl+K" }  # 复用 AI 中台入口
│   { "action":"ai.assist",        "win":"SmartKey" } # 智慧键唤起
├─ keyboardLayoutOverrides:                          # 国际化覆盖（Figma 经验）
│   DE: { "decreaseTextWeight":"Ctrl+Alt+ẞ" }        # 规避 ß→SS 大小写坑
│   FR: { ... }  JA: { ... }  KO: { ... }
```

**国际化要点**（来自 Figma 工程复盘）：
- 用**位置码（KeyCode）而非字符**做主键，运行时按用户键盘布局映射到实际字符显示。
- 预置德/法/日/英/西/中/韩等主流布局覆盖；Figma 实测 30 天内出现 2500+ 种布局，需检测逻辑兜底。
- 特殊字符（如 `ß`）大小写归一有陷阱，用 `ẞ` 大写 eszett 规避。

### 11.2 UI 显示规划：响应式画布工作区

#### 11.2.1 鸿蒙响应式基础（已核查事实）

- **单位**：`vp`（虚拟像素，密度自适应）+ `fp`（字体像素，随系统字号缩放）。
- **网格**：8vp 基础网格（图标对齐 4vp）。
- **横向断点**：xs(0,320) / sm[320,600) / md[600,840) / lg[840,1440) / xl[1440,+∞)。
- **纵向断点**：sm(0,0.8) / md[0.8,1.2) / lg[1.2,+∞)（高宽比）。
- **栅格**：0–600vp→4 列；600–840→8 列；840+→12 列。
- **响应式组件**：`GridRow/GridCol`（栅格）、`Navigation`（单/双栏）、`SideBarContainer`（侧栏）、`Tabs`、`WaterFlow`、`Swiper`、`List`。
- **断点读取**：API 22+ 用 `@Env` 装饰器读断点环境变量，窗口变化自动刷新。
- **关键机型断点**：MateBook Pro 全屏 = **xl / sm**；MateBook Fold 展开 = **xl / sm**；MatePad Pro = lg / sm；Mate X5 内屏 = md / md。

#### 11.2.2 画布工作区布局（按断点分三档）

| 断点 | 形态 | 布局 |
|---|---|---|
| **xl / lg（PC、大平板横屏）** | 桌面工作区 | **三栏**：左（工具栏 + 资源库/字体面板）+ 中（无限画布 + 浮动工具选项）+ 右（属性检查器 + 图层面板 + 样式） |
| **md（平板、折叠展开）** | 平板工作区 | **双栏**：左（可收起工具栏）+ 中画布，右栏以 `SideBarContainer` 抽屉形式滑出；手写笔绘制优化 |
| **sm / xs（手机、竖屏）** | 移动工作区 | **单栏 + 底部工具抽屉**：画布全屏，工具/属性以底部 Sheet + 径向菜单呼出，查看/轻改为主 |

#### 11.2.3 折叠屏 / 双屏专属适配

- **MateBook Fold（展开 1832×1374，xl）**：副屏放工具/属性/参考素材，主屏放画布——**双屏工作流**是鸿蒙 PC 独有红利，类比 18 寸折叠创作形态，Mac/Windows 无对应产品。
- **Mate X 系列（展开 md/lg）**：展开态走双栏，折叠态走单栏；**避让折痕区**（转轴处不放关键控件/画布中心内容）。
- **悬停态**（内折/外折悬停）：下半屏做控制面板，上半屏预览。

#### 11.2.4 显示模式与规范性

- **深色/浅色**：跟随系统，但工作区用**中性灰阶梯**（不纯黑不纯白），避免干扰色彩判断（设计软件通用实践）。
- **高 DPI / 缩放**：用 `fp` 单位规避系统字号放大导致的布局错位；画布缩放独立（Ctrl+=/-）。
- **安全区**：手机/折叠/平板避让信号栏、底部导航条、两侧 margin；折叠设备避让转轴区。
- **与华为官方规范协调**：沿用鸿蒙 8vp 网格、组件密度语言，保证"不像外来应用"；但工作区专业密度高于普通 App，需在规范框架内做密度提升。

### 11.3 可用性规划：可学习、可发现、容错、无障碍

#### 11.3.1 降低学习曲线（AI 中台作为渐进式引导）

- **首图即上手**：新用户不必先学钢笔工具——输入"做一张咖啡店开业海报，复古风"，AI 中台生成首稿，用户在成品上改。学习曲线从"先学工具"变为"先出成果，再学精修"。
- **上下文教学**：用户选中某对象时，属性面板显示"你可以用 Ctrl+T 变换"等渐进提示，而非一次性灌输。

#### 11.3.2 可发现性

- **命令面板（Ctrl+K）**：模糊搜索所有命令 + 唤起 AI 指令，复用 AI 中台入口（一框两用）。
- **快捷键提示面板**（借鉴系统鸿蒙键+?）：应用内 `?` 唤起完整快捷键参考。
- **工具提示 / 空状态设计**：首次进入展示模板与引导，而非空白画布。

#### 11.3.3 容错与性能

- **无限撤销/重做**：接第 10.7 历史分支，非破坏编辑（调整层/智能对象可回退）。
- **可中断异步**：AI 生图/生矢量走云端，进度条可取消，不阻塞画布。
- **操作反馈 < 16ms**：本地渲染（Skia）保证笔触/变换实时；重型操作转后台线程。

#### 11.3.4 跨端一致性

- 同一 `.hds` 文档模型，PC 精修 / 平板笔绘 / 手机查看，状态经云同步；功能对等（11.1.5），体验分级（11.2.2）。

#### 11.3.5 无障碍（WCAG 2.1 AA）

| 维度 | 措施 |
|---|---|
| 键盘全导航 | 所有功能可键控（不依赖鼠标/触控） |
| 焦点指示 | 清晰焦点环（对比度达标，高对比模式仍可见） |
| 对比度 | UI 文本 ≥ 4.5:1，图形元素 ≥ 3:1 |
| 屏幕阅读器 | ArkUI 无障碍属性标注 |
| 色盲模拟 | 内置色盲预览（验证配色可辨识） |
| 非色彩依赖 | 状态不只靠颜色区分（加图标/文字） |

### 11.4 三者统一于约束的总结

| 规划层 | 约束契合点 | 双发行版/双形态处理 |
|---|---|---|
| **快捷键** | 四模态 → 同一命令注册中心（复用 AI 中台） | 物理键 PC 同码；移动端用手势/笔/语音对等，功能不丢 |
| **UI 显示** | ArkUI 断点 + 栅格 + 响应式组件官方体系 | 按断点分三档布局，文档模型共享，仅 UI 层分形态 |
| **可用性** | AI 渐进引导 + 命令面板 + 无障碍 | 共享规范与组件；系统无障碍能力按平台 adapter 验证 |

**结论**：快捷键、UI 和可用性主要落在 ArkTS/ArkUI 与输入适配层；HarmonyOS 与 OpenHarmony 共享交互契约、Command 和大部分 UI 组件，但系统保留键、输入设备、窗口、多屏和 API 可用性必须经过 capability matrix 与 Platform Port 适配。PC/移动共享文档模型与命令层，按输入模态和工作区布局分别实现，目标是最大化复用而不是承诺零差异。

### 12.2 文件与项目管理

- **项目单位**：以 `.hds` 文件为中心，但项目层支持文件夹与模板工程。
- **项目结构**：
  - `project.hdsproj`：工程索引，记录最近文档、资源库、导出预设、协作状态。
  - `assets/`：共享资源库，可被多个 `.hds` 文件引用。
  - `templates/`：海报、画册、名片、社媒封面、演示稿模板。
- **打开策略**：启动页分为“最近项目 / 模板 / 导入 / 新建 / 团队空间”。
- **多文档工作区**：支持标签页、分屏、拖拽文档窗口，PC 端优先，移动端简化为最近文档+单文档。

### 12.3 资源管理

- **资源类型**：字体、色板、渐变、笔刷、符号、模板、预设、外链图片、嵌入素材。
- **资源去重**：同一资源按哈希与引用计数管理，避免大文档重复嵌入。
- **资源库**：支持本地库、团队库、只读共享库。
- **AI 关联**：每次 AI 生成对象必须记录资源来源，便于可复现与版权追踪。

### 12.4 历史 / 版本 / 分支

- **命令栈**：所有编辑动作都落成命令，保证撤销/重做一致。
- **版本点**：支持手动保存快照、自动保存快照、导出快照。
- **分支历史**：从任意版本点可分叉，适合设计探索与客户迭代。
- **冲突恢复**：协作场景下按对象粒度合并，失败则回退到安全版本。

### 12.5 协作 / 批注 / 共享

- **协作范围**：先做“异步协作”——共享查看、批注、评论、任务指派；再做实时光标与同步编辑。
- **评论模型**：评论绑定到页面、图层、对象、文本区间。
- **权限**：拥有者 / 编辑者 / 评论者 / 只读者。
- **同步基础**：文档命令流 + 对象 ID + 变更时间戳，为后续 CRDT 或 OT 留接口。

### 12.6 插件 / 扩展 / 脚本

- **插件形态**：工具插件、面板插件、导入导出插件、AI 动作插件。
- **脚本接口**：开放一层受限脚本 API，只允许操作文档命令，不直连底层渲染。
- **扩展边界**：插件可新增工具和面板，但不得绕过权限系统直接读写本地私密资源。
- **生态策略**：先内置官方插件市场，后开放第三方签名包。

### 12.7 导入 / 转换 / 迁移流程

- **导入流程**：识别格式 → 建立映射 → 生成 Fusion DOM → 资源外置 → 标记兼容损失。
- **迁移优先级**：SVG / ODG / EPS / PSD / AI / IDML / OpenRaster 分层支持，先可读、再可写。
- **兼容提示**：导入后自动提示“哪些特性被折算、哪些可继续编辑、哪些仅保留渲染结果”。
- **迁移策略**：把 Adobe 私有格式作为迁移输入，不作为长期锁定输出。

### 12.8 发布 / 上架 / 交付

- **上架分流**：HarmonyOS 走华为应用市场；OpenHarmony 走对应发行版商店或企业侧分发。
- **交付形态**：个人版、专业版、团队版、企业版。
- **导出预设**：屏幕、社媒、电商、印刷、归档、无障碍。
- **版本门槛**：P0 先满足核心设计与导出，P1 扩展 AI，P2 开放协作与插件市场。

### 12.9 性能 / 缓存 / 大文档

- **渲染缓存**：按页面、图层、对象建立分级缓存；重复路径和文本走局部重绘。
- **资源缓存**：字体、缩略图、画板预览、AI 结果、导入转换中间态均可缓存。
- **大文档策略**：懒加载、分片保存、滚动可见区域优先绘制。
- **内存上限**：移动端与 PC 端采用不同默认阈值，避免大图/多页文档拖垮前台。

### 12.10 安全 / 隐私 / 权限

- **本地优先**：文档默认本地保存，云端仅同步用户显式开启的内容。
- **权限最小化**：文件、相机、麦克风、剪贴板、网络权限均按需申请。
- **AI 数据边界**：发送到云端模型前必须明确标识“文档片段 / 画布截图 / 资源引用”，用户可单独关闭。
- **安全导出**：导出的 PDF / `.hds` 可选择去除历史和 AI 上下文。

### 12.11 测试 / 验收 / 质量门禁

- **单元测试**：DOM、命令、导入转换、快捷键映射。
- **集成测试**：Skia 渲染、PDF 导出、AI 协议层、断点适配。
- **回归测试**：大文档、撤销重做、跨发行版打开、导入导出损耗。
- **验收指标**：打开速度、首帧时间、笔触延迟、导出成功率、跨端一致性、崩溃率。

### 12.12 补强后的产品分层

| 层级 | 核心内容 |
|---|---|
| 输入层 | 快捷键 / 手势 / 手写笔 / 语音 + AI |
| 交互层 | 响应式 UI、命令面板、无障碍、工具栏 |
| AI 协议层 | 模型无关协议、能力注册表、路由、BYOK |
| 文档层 | Fusion DOM、命令栈、历史分支、资源引用 |
| 引擎层 | Skia、FreeType、HarfBuzz、ICU、lcms2、PDFium/libHaru |
| 格式层 | `.hds` + SVG/ODG/EPS/PDF 2.0/PDF/X-4/OpenRaster 等 |
| 协作层 | 批注、共享、权限、同步 |
| 扩展层 | 插件、脚本、导入导出扩展 |
| 能力开放层 | Command Registry 对外投影：CLI、MCP Server/Client、Skill Runtime、Plugin API |
| 作业与治理层 | Job 队列、权限、审计、配额、Entitlement、计费、风控 |
| 发布层 | 上架、导出预设、企业分发、质量门禁、插件/Skill 市场 |

**补强结论**：现有计划已经证明“能做”，第 12 章补齐的是“能交付、能扩展、能长期演进”。实现采用 ArkTS/ArkUI 客户端、平台无关契约/Fusion Core、开源引擎和模型无关协议层；系统能力通过 Platform Port 隔离，不把 HMS 或 OpenHarmony 发行版 API 渗入核心领域。

## 13. MCP、CLI、Skill 与会员订阅规划

本章补足前 0–12 章未覆盖的四个关键系统。它们不是孤立附加功能，而是围绕同一条主线构成完整闭环：

> **Command Registry 定义能力 → GUI / CLI / MCP 暴露能力 → Skill 编排能力 → 会员与组织授权管理规模化使用。**

### 13.1 MCP 协议规划：软件既是 Server，也是 Host/Client

#### 13.1.1 双角色定位

**MCP Server**：让外部 AI 客户端或 Agent 操控本软件。

- `document.*`：新建、读取、保存、页面管理。
- `selection.*`：查询选区、对齐、分布、变换。
- `vector.*`：路径、形状、布尔运算、描边、填充。
- `bitmap.*`：导入、裁切、滤镜、抠像、局部编辑。
- `layout.*`：文本、样式、分栏、串流、自动排版。
- `export.*`：预览、导出、打包、印刷预检。

**MCP Host/Client**：让软件连接外部 MCP Server，用于素材搜索、字体、云存储、外部模型、版权检查等。

两种角色必须共用身份、权限、审计和任务系统；不允许 MCP 处理器直接写 Fusion DOM，所有写操作必须转换为内部 Command，经过事务、撤销/重做和权限检查。

#### 13.1.2 MCP 能力映射

| MCP 能力 | 本软件映射 |
|---|---|
| Tools | Command Registry 中经过审核的工具函数 |
| Resources | `.hds` 文档快照、页面、选区、素材、预览图、任务产物 |
| Prompts | 社媒套图、品牌检查、杂志排版等可审阅模板 |
| Tasks / progress | 批量导出、AI 生图、批量排版、印前预检等异步任务 |

建议资源 URI：

```text
design://documents/{id}
design://documents/{id}/pages/{pageId}
design://documents/{id}/selection
design://assets/{hash}
design://jobs/{jobId}/result
```

#### 13.1.3 传输与兼容

- **stdio**：本机 AI 客户端连接，使用受限桥接子进程；`stdout` 只输出 JSON-RPC，日志走 `stderr`。
- **Streamable HTTP**：远程 Agent、团队和企业场景；服务端仅绑定受控地址，使用 TLS 与 OAuth 2.1/PKCE。
- 生产基线建议兼容 MCP `2025-11-25`，同时隔离协议适配器，以便跟进后续规范变化；协议版本、软件 API 版本和 Tasks 扩展版本分别管理。
- 不设计万能 `execute_command`；只暴露经过审核的领域工具，防止外部 Agent 获得任意写入能力。

#### 13.1.4 任务、资产与安全

- 短操作同步返回；批量导出、AI 生图和多页排版进入持久化 Job/Task。
- 任务支持 `working → input_required → completed/failed/cancelled`，支持进度、轮询、取消和事务回滚。
- 大型图片、字体、PSD 和导出包不直接塞入 JSON；使用带 MIME、字节数、SHA-256 的 `resource_link`，远程使用短期单用途 HTTPS 地址。
- 权限按“连接身份 × 文档 × 能力 × 有效期”授予。读取、预览可会话授权；写入、覆盖、导出、上传、外部网络和批量操作需要分级审批。
- 外部 Tool 描述、Prompt 和 Resource 内容均视为不可信输入，不能改变权限判断或系统策略。

### 13.2 CLI 规划：统一的自动化与无界面入口

建议可执行文件名为 `hds`，定位为人工、脚本、CI/CD 和 Agent 的确定性入口。

```text
hds
├─ document  new|info|validate|migrate|diff|apply
├─ node      get|query|insert|update|remove|reorder
├─ asset     list|import|replace|optimize|extract
├─ render    preview|export|thumbnail
├─ batch     run|validate
├─ command   list|describe|run
├─ job       submit|status|logs|result|cancel
├─ engine    list|probe|use
├─ plugin    list|inspect|install|enable|disable|remove
├─ skill     list|inspect|validate|install|run|pack|publish
├─ ai        plan|generate|edit
├─ mcp       serve
└─ config|doctor|completion|version
```

CLI 不单独实现业务逻辑；所有命令最终调用 Command Registry。统一参数约定：

```text
--output auto|text|json|ndjson
--input <file|->
--args <file|@->
--output-file <path>
--request-id <id>
--idempotency-key <key>
--timeout <duration>
--non-interactive
```

- TTY 下 `auto` 输出人类可读文本，管道/CI 场景默认 JSON；`stdout` 只承载结果，`stderr` 承载日志与进度。
- 长任务使用 NDJSON 事件：`accepted / progress / log / artifact / completed / failed`，最后一行必须是终态事件。
- 退出码统一：`0` 成功、`2` 参数错误、`3` 输入不存在、`4` 冲突、`5` 权限拒绝、`6` 环境缺失、`7` 引擎不可用、`8` 超时、`9` 取消、`10` 部分成功、`70` 内部错误。
- 作业记录参数快照、输入摘要、Registry 版本、引擎版本、Skill 锁文件、产物和审计日志，确保 CI 可追溯。

### 13.3 Skill 规划：声明、指导与编排包

Skill 与插件必须明确区分：

- **Skill**：描述“何时使用、按什么步骤、调用哪些能力”，偏编排和知识。
- **插件**：提供“新增工具、面板、导入器或运行时能力”，偏可执行扩展。
- **CLI**：提供确定性的命令执行面。
- **MCP**：提供面向 Agent 的发现、资源和工具调用协议。

建议 Skill 包结构：

```text
SKILL.yaml
schemas/
workflows/
scripts/
assets/
README.md
```

最低 manifest：

```yaml
apiVersion: hds.skill/v1
name: brand-batch-export
version: 1.2.0
entrypoints: [export-campaign]
commands: [design.node.query, design.render.export]
permissions:
  filesystem: {read: [workspace/**], write: [dist/**]}
  network: {domains: []}
runtime: {sandbox: required}
```

强制规则：

- 默认拒绝权限；明确声明文件范围、网络域名、进程启动、密钥引用、模型调用、文档写入和远程执行权限。
- 输入输出必须使用 JSON Schema，默认 `additionalProperties: false`。
- 使用 SemVer；安装解析后生成锁文件，锁定 Skill、插件、Schema、Registry 版本和内容摘要。
- 脚本进入独立沙箱，限制目录、网络、CPU、内存、时间和子进程；密钥只能以临时引用注入，不进入日志或产物。
- 发布包使用 SHA-256、发布者签名、SBOM 和来源证明；市场支持审核、撤回、吊销和企业可信发布者策略。
- 禁止隐式下载依赖与循环依赖。

## 14. 统一认证与客户端/后端架构选型

本章把统一认证、后端边界和后续 Windows 演进纳入正式架构。截图中的统一认证服务识别为 **Casdoor**（`casbin/casdoor` + PostgreSQL），但仓库不写入具体生产地址、密钥或租户配置；这些属于部署环境参数。

### 14.1 统一身份、组织与资产治理（遵循平台规范）

本节遵循平台权威文档 `F:\Casdoor认证服务\casdoor\UNIFIED_ASSET_GOVERNANCE.md`（由 `AGENTS.md` 引用），以下称《治理规范》。该规范对 Casdoor 组织、应用、用户、角色、权限、余额、积分、支付和项目接入具有最高优先级；本设计软件作为接入项目必须遵守。

#### 14.1.1 三类组织概念（禁止混用）

《治理规范》第 2 节明确区分三类组织，本项目的所有权限、资产和结算判断必须按此分类：

| 概念 | 标识 | 职责 | 权威系统 |
|---|---|---|---|
| 身份组织 | Casdoor `organization`，业务值为 `platform` | 登录策略、MFA、账户字段、应用认证策略 | Casdoor |
| 业务组织 | `businessOrganizationId` | 企业/部门/项目主体、数据和业务权限边界 | 组织成员关系服务（独立于 Casdoor） |
| 结算域 | `settlementDomainId` | 统一现金余额可否共用的资金边界 | 平台钱包中心 |

一个用户只有一个 `platform` 身份组织，但可以有零到多个业务组织成员关系，每个成员关系独立记录角色、项目、有效期和结算域。**禁止用 Casdoor `user.groups` / `properties` 模拟业务组织成员关系。**

#### 14.1.2 当前组织上下文（每次请求必须验证）

登录只证明“是谁”；业务操作还必须证明“当前代表哪个有效组织工作”。授权链路按《治理规范》第 4 节固定为：

1. Casdoor 验证 OIDC/OAuth 令牌，得到可信 `issuer + sub` 和应用身份。
2. 组织成员关系服务查询该主体可用的业务组织和角色。
3. 用户选择当前业务组织；服务端生成**短时组织上下文**，不能信任浏览器自行提交的组织 ID。
4. 业务应用每次读写同时校验 `issuer + sub`、`membershipId`、`businessOrganizationId`、`applicationId` 和业务权限。
5. 成员关系被暂停、撤销或到期后，组织上下文立即失效；全局登录身份可保留。

本设计软件的 Go API 必须在 `/api/v1/documents`、`/api/v1/commands`、`/api/v1/jobs` 等所有写接口执行上述五元校验，不得仅凭 `issuer + sub` 放行。

#### 14.1.3 四类资产账户键（权威定义）

《治理规范》第 5 节定义四类资产，账户键和权威各不相同，本项目必须按此实现，不得自创 `product_id + wallet_scope + unit` 模型：

| 资产 | 账户键 | 唯一权威 | Casdoor 定位 |
|---|---|---|---|
| 统一现金余额 | `issuer + sub + settlementDomainId + currency` | 平台钱包中心 | `user.balance` 仅只读展示投影 |
| 项目业务余额 | `projectId + businessOrganizationId + issuer + sub + assetType` | 对应项目业务系统 | 不存储 |
| 项目积分 | `projectId + businessOrganizationId + issuer + sub + pointType` | 对应项目积分系统 | 不存储 |
| 身份信誉积分 | `issuer + sub` | Casdoor | `user.score` |

本设计软件涉及的资产映射：

```text
统一现金余额：
  issuer + sub + settlementDomainId + currency=CNY
  → 权威：平台钱包中心；Casdoor user.balance 只读投影

设计软件项目积分（AI 点数）：
  projectId=hds + businessOrganizationId + issuer + sub + pointType=HDS_CREDIT
  → 权威：本设计软件 Go 后端积分模块

设计软件项目业务余额（套餐储值，若启用）：
  projectId=hds + businessOrganizationId + issuer + sub + assetType=HDS_STORE
  → 权威：本设计软件 Go 后端业务余额模块

身份信誉积分：
  issuer + sub
  → 权威：Casdoor user.score；不可兑换、抵扣或结算
```

#### 14.1.4 平台钱包中心与项目账本协作

《治理规范》第 6 节规定：统一现金余额由平台钱包中心保存不可变流水，项目保存自己的订单、履约、业务余额、项目积分和业务账本。两类账本职责不同，不能相互替代。

钱包动作使用规范定义的六态，不是自创的 reservation/settle：

| 动作 | 作用 | 结果 |
|---|---|---|
| 充值入账 | 外部支付或人工核验成功后增加现金余额 | `credited` |
| 付款预授权 | 项目准备消费时冻结可用余额 | `held` |
| 确认扣款 | 项目服务履约后完成扣款 | `captured` |
| 释放预授权 | 订单取消、超时或失败时解冻 | `released` |
| 退款 | 对已完成消费执行原路或余额退款 | `refunded` |
| 冲正 | 对已入账错误执行反向流水 | `reversed` |

本设计软件消费统一现金余额（例如 AI 生图扣费）必须遵循：创建本地待支付记录 → 携带有效组织上下文向钱包中心请求 `held` → 履约后 `captured` → 失败则 `released`/`refunded`/`reversed` → 按日对账。金额、状态、组织或订单引用不一致时进入异常队列，禁止静默修正余额。

**金额规则**：所有现金金额在钱包中心以最小货币单位整数计算和保存（《治理规范》第 1 节），不得用 float64 参与结算。Casdoor `User.Balance` 当前为 `float64`，只能作为受控展示投影。

#### 14.1.5 Casdoor 数据使用边界

按《治理规范》第 7 节，本项目对 Casdoor 数据的使用边界：

| Casdoor 数据 | 本项目允许用途 | 禁止用途 |
|---|---|---|
| `user.owner` | 识别唯一身份组织 `platform` | 表示业务组织成员关系 |
| `user.balance` / `balanceCurrency` | 钱包中心同步的只读展示摘要 | 扣款权威、资金流水、项目直接写入 |
| `user.score` | 身份信誉积分展示 | 项目积分、现金、折扣或抵扣 |
| `user.groups` | 不使用 | 业务组织成员关系权威 |
| `user.properties` | 非财务外部引用 | 组织成员、现金余额、项目积分、账本流水 |
| Casdoor `application` | 本项目接入应用、回调地址、令牌受众 | 项目钱包或账本 |
| 全局 `role` / `permission` | 平台级操作授权 | 业务组织内数据权限或账务凭据 |

本项目不修改 Casdoor 后端数据库字段、索引或迁移；不为业务组织复制 Casdoor 用户；不把 Casdoor `properties` 当作组织成员或账本权威；不绕过平台钱包中心直接写入或扣减 `user.balance`。

#### 14.1.6 新项目接入检查清单

按《治理规范》第 10 节，本设计软件接入必须完成：

- [ ] 在 `platform` 身份组织创建独立 Casdoor `application`，配置真实回调地址和最小认证范围。
- [ ] 声明可接入的业务组织、结算域和所需成员角色。
- [ ] 用 `issuer + sub` 建立身份映射，用成员关系服务验证当前业务组织。
- [ ] 业务请求保存并校验 `membershipId`、`businessOrganizationId` 和 `applicationId`。
- [ ] 实现自己的业务账本，把钱包交易标识写入订单/账本引用。
- [ ] 所有支付、退款、冲正接口实现幂等键、订单唯一性和组织上下文校验。
- [ ] 项目业务余额、项目积分、统一现金余额和身份信誉积分在 UI 中分开命名、分开查询。
- [ ] 配置项目服务身份为最小 `membership.*` / `wallet.*` 权限。
- [ ] 完成多组织登录、组织切换、权限撤销、正常扣款、重复请求、超时释放、退款、冲正和日对账演练。

**统一身份主键**：业务库使用内部 `account_id` 作为主键，外部关联使用 `issuer + casdoor_sub`；禁止用邮箱作为永久主键。业务组织成员关系唯一键为 `issuer + subject + businessOrganizationId`。

### 14.2 Casdoor OIDC 接入基线

客户端和服务端均采用 **Authorization Code + PKCE（S256）**。客户端不保存 client secret，服务端只在需要交换或管理受信任后端流程时使用机密凭据。

部署时必须通过 Casdoor 的 OpenID Discovery 获取真实端点，不在代码中硬编码猜测值：

```text
{CASDOOR_URL}/.well-known/openid-configuration
```

预期使用的协议端点：

```text
authorization_endpoint: {CASDOOR_URL}/login/oauth/authorize
token_endpoint:       {CASDOOR_URL}/api/login/oauth/access_token
logout_endpoint:      {CASDOOR_URL}/api/sso-logout
jwks_uri:             以 Discovery 返回值为准
issuer:               以 Discovery 返回的 issuer 为准
```

**首次部署前必须确认的配置契约**：

```text
CASDOOR_URL
OIDC_ISSUER
organizationName
applicationName
client_id
redirect_uri（HarmonyOS / OpenHarmony / PC 分别登记）
audience 或 resource URI
scope（openid profile email offline_access，按服务端能力启用）
```

客户端流程：

1. 生成高熵 `code_verifier`，计算 `code_challenge=S256`，同时生成一次性 `state` 与 `nonce`。
2. 通过系统安全浏览器打开 Casdoor 授权页；不在 WebView 内嵌登录，降低凭据泄露和兼容性风险。
3. 回调只接收授权码，校验 `state` 后交换令牌；Access Token 不进入日志、剪贴板或普通持久化文件。
4. 使用系统安全存储保存 refresh token 或受保护的令牌材料；Access Token 短时缓存并在内存中使用。
5. 首次调用业务 API 时，服务端校验 JWT 的 `iss/aud/exp/iat/nbf/nonce/sub` 与签名算法，再按 `casdoor_sub` 幂等创建或更新本地 Account。
6. Refresh rotation、撤销、登出和异常设备下线以服务端返回为准；客户端必须能处理 401、令牌过期和重新授权。

**安全要求**：Discovery/JWKS 缓存要有过期时间和密钥轮换处理；仅接受 HTTPS；严格校验 redirect URI；不接受从客户端直接提交的 `account_id`、`tenant_id` 或 entitlement 作为授权依据。

### 14.3 Go 后端推荐架构：模块化单体优先

第一阶段采用 **Go 模块化单体 + 明确领域边界**，而不是一开始部署大量微服务。这样保留未来拆分能力，同时减少认证、文档事务、作业和审计之间的分布式一致性成本。

```text
Go API（net/http + chi）
├─ transport：REST / SSE / WebSocket（按需）/ MCP HTTP adapter
├─ middleware：OIDC JWT、request-id、幂等、限流、审计上下文
├─ application：Account、Document、Asset、Command、Job、Entitlement
├─ domain：Fusion DOM 契约、权限策略、状态机、配额规则
├─ infrastructure：PostgreSQL、Redis、NATS、S3、Casdoor JWKS
└─ worker：AI 任务、导入导出、缩略图、批处理、病毒/版权检查
```

推荐技术栈与边界：

| 能力 | 首选 | 使用边界 |
|---|---|---|
| HTTP/API | Go `net/http` + `chi` | 标准库承载基础能力，`chi` 只做路由和中间件组合 |
| 数据库访问 | PostgreSQL + `pgx` + `sqlc` | SQL 显式审查、类型安全；迁移使用 Atlas 或 Goose，二选一 |
| 缓存/短状态 | Redis | 令牌黑名单、幂等键、限流、短期锁；不作为文档事实库 |
| 异步作业 | NATS JetStream | AI、导入导出、批处理和通知；Job 状态最终回写 PostgreSQL |
| 对象存储 | S3-compatible | `.hds` 大资源、缩略图、导出产物；私有化可用 MinIO |
| 可观测性 | OpenTelemetry + Prometheus + Loki/Tempo/Grafana | trace_id 贯穿 API、Job、模型请求和审计 |
| API 契约 | OpenAPI 3.1 + JSON Schema | REST、CLI、MCP 参数共用 schema，禁止三套字段漂移 |
| CLI | Go Cobra | 调用同一 application/Command 层，不复制业务逻辑 |
| MCP | MCP Go SDK 或受控适配层 | 工具白名单、资源链接、审批、取消、审计必须由治理层统一处理 |

**不建议首期引入**：Kubernetes、服务网格、OpenSearch、复杂事件溯源和多活数据库。等文档搜索、组织规模或部署形态证明需要后再增加，避免基础设施先于产品验证。

### 14.4 首期 API 契约（认证闭环最小垂直切片）

API 统一使用 `/api/v1`、Bearer Token 和结构化错误；成功响应使用 `{data: ...}`，写入失败不得用 200 伪装成功。

```text
GET  /api/v1/me
GET  /api/v1/memberships                     # 当前用户可用的业务组织成员关系
POST /api/v1/memberships/{id}/context        # 切换当前业务组织上下文（短时令牌）
GET  /api/v1/entitlements?projectId=hds&businessOrganizationId={org}
GET  /api/v1/project-points?projectId=hds&businessOrganizationId={org}&pointType=HDS_CREDIT
GET  /api/v1/documents
POST /api/v1/documents
GET  /api/v1/documents/{document_id}
POST /api/v1/documents/{document_id}/commands
POST /api/v1/jobs
GET  /api/v1/jobs/{job_id}
POST /api/v1/jobs/{job_id}/cancel
```

统一现金余额的预授权、扣款、释放、退款、冲正不由本项目 API 直接承载，而是由本项目服务身份携带有效组织上下文调用**平台钱包中心**接口（`held`/`captured`/`released`/`refunded`/`reversed`），并把钱包交易标识写回本地订单和业务账本。项目积分（`HDS_CREDIT`）由本项目积分模块直接维护，但同样遵循幂等、审计和对账规则。

最小登录闭环：

```text
ArkTS 客户端
  → Casdoor Authorization Code + PKCE
  → Access Token
  → Go API /api/v1/me
  → JWT/JWKS 校验
  → PostgreSQL accounts（casdoor_sub 幂等映射）
  → Account + Entitlement 返回客户端
```

`POST /documents/{id}/commands` 必须包含 `command_type`、版本化参数、`request_id` 和可选 `idempotency_key`；服务端按文档权限开启事务，写入命令审计，再更新文档版本。AI、CLI、MCP 和 GUI 最终都走这条命令路径。

### 14.5 ArkTS/ArkUI 客户端分层

客户端先做鸿蒙原生，但分层必须为 Windows 留出共享核心：

```text
ArkUI Shell（页面、导航、面板、断点、无障碍）
        ↓
Feature/UI State（登录、文档、画布、AI、资源）
        ↓
Application/Command（与 GUI、CLI、MCP 共用契约）
        ↓
Platform Ports（网络、浏览器回调、安全存储、文件、输入、窗口）
        ↓
Fusion Core（DOM、解析、命令、排版、渲染接口）
        ↓
C/C++ 或 Rust Engine（Skia、字体、色彩、格式）
```

HarmonyOS/OpenHarmony 共享 ArkTS 业务与 Fusion Core；差异通过 `PlatformCapability` 注入，包括安全存储、系统浏览器回调、文件选择器、窗口/多屏、分发和 IAP。移动端与 PC 端不是简单缩放，而是共享文档和命令、分别实现输入与工作区布局。

登录页只负责启动授权和展示状态，不自行解析或信任余额、积分或业务权益。建议封装 `AuthRepository`、`TokenStore`、`OidcBrowserFlow`、`UserCenterClient` 和 `AccountRepository`；业务客户端通过服务端获取带 `product_id`、`scope`、`unit`、`version` 的权益与钱包快照，并为回调、401、刷新失败、权限撤销和离线只读模式编写状态机测试。

### 14.6 Windows 演进策略

Windows 不作为鸿蒙客户端的“加一个断点”处理。可复用的部分应提前定义为跨端核心：Fusion DOM schema、Command schema、解析器、排版规则、资源哈希、Job/API/OpenAPI 和渲染金样。

推荐顺序：

1. 鸿蒙先验证 ArkUI 工作区、平台端口和 NAPI 引擎接口。
2. 将 Fusion Core 独立为 C++/Rust 核心库，提供稳定 C ABI；ArkTS 通过 NAPI，Windows 通过 C ABI/语言绑定接入。
3. Windows UI 在验证核心契约后选择 Qt 6 或原生 Windows UI；不要让 Windows UI 选择反过来污染鸿蒙首版。
4. 用同一组 `.hds`、SVG、PDF、渲染金样和命令回放测试验证跨端一致性。

Windows 复用核心的前提是：不依赖 `@ohos.*` 的 Fusion Core、协议和数据层；系统浏览器、文件、输入、窗口、通知和支付都属于平台适配层。

### 14.7 成熟开源库与自研边界

原则是“成熟库解决通用难题，核心算法形成产品差异”：

| 领域 | 优先复用 | 应自研 |
|---|---|---|
| 渲染 | Skia | Fusion DOM 到 DisplayList 的增量编译、缓存策略 |
| 字体/排版 | FreeType、HarfBuzz、ICU | 中文禁则、版式约束、文本流和样式系统 |
| 色彩 | LittleCMS 2 | 产品色板、软打样工作流和印前检查规则 |
| 图像 | libpng、libjpeg-turbo、libwebp、OpenCV（可选） | 非破坏调整层、蒙版语义和设计操作链 |
| PDF/EPS | PDFium、libHaru、Ghostscript（按许可和体积审查） | Fusion DOM 映射、印刷预检和导出策略 |
| 数据/API | pgx、sqlc、OpenAPI、JSON Schema | 领域模型、Command Registry、权限和审计语义 |
| 协作 | CRDT 库（候选，需实测） | 对象级合并策略、冲突可视化和版本体验 |

每个库在进入主干前需记录版本、许可证、目标 ABI、HarmonyOS/OpenHarmony 构建状态、Windows 构建状态、测试覆盖和替代方案；不能因为“开源”就跳过许可证与供应链审查。

### 14.8 趋势复核与架构冻结条件

**复核结论：方向符合当前技术趋势，但原计划不能直接冻结实施。** 合理的趋势项包括：模型无关 AI、BYOK、开放格式、MCP/CLI/Skill、模块化单体、事件驱动作业、OpenTelemetry、跨端共享核心和本地优先数据。需要修正的表述和结构如下：

- 将“一套代码零差异”改为“核心业务、数据和协议共用；平台能力按 capability matrix 适配”。字体回退、文件授权、系统浏览器、窗口、多屏、IAP 和发行渠道都可能产生真实差异。
- 将 Phase 1–6 从单纯功能堆叠改为“契约优先 + 可验证垂直切片”：先冻结 `Fusion DOM / Command / Job / Resource / Capability / Permission / Audit / Entitlement` 八项契约，再扩展功能。
- `.hds` 的 `history/`、`ai/` 和大资源应支持可选、可剥离和隐私清理；默认不把敏感提示词、远程 endpoint 或完整历史无条件打包。
- MCP、CLI、Skill 不应全部推迟到产品后期；Phase 1 就应做一个只读/单写命令的垂直切片，验证 schema、权限、审计和回放。
- 必须建立真实设备 CI、HarmonyOS/OpenHarmony 双构建、渲染金样、格式往返、命令回放、性能门禁和依赖许可证扫描。
- Go 后端首期以模块化单体承载业务；只有当组织隔离、任务吞吐、团队部署或合规要求证明必要时再拆服务。

**架构冻结的验收门槛**：

```text
1. HarmonyOS 真机完成登录 → /me → 新建文档 → 保存 .hds
2. OpenHarmony 目标设备完成同一流程，且不引入 HMS 私有依赖
3. Go API 通过 issuer/audience/JWKS/nonce/过期校验测试
4. 同一 Command 可由 GUI、CLI、MCP 之一执行并产生日志与可回放结果
5. .hds、SVG、PDF 至少完成一组导入/导出往返和渲染金样对比
6. 关键依赖完成许可证、SBOM、漏洞和 ABI 记录
7. Windows 共享核心的 C ABI 与平台端口完成编译样例，不要求首期交付完整 UI
```

**最终选型结论**：客户端采用 ArkTS/ArkUI 原生 + NAPI/C++（必要时 Rust）Fusion Core；后端采用 Go `net/http` + `chi` 的模块化单体，配 PostgreSQL/pgx/sqlc、Redis、NATS JetStream、S3-compatible 对象存储和 OpenTelemetry；身份、组织和资产治理遵循 `F:\Casdoor认证服务\casdoor\UNIFIED_ASSET_GOVERNANCE.md`：Casdoor 负责唯一身份（`platform` 身份组织）和平台级授权，业务组织成员关系由独立成员关系服务维护，统一现金余额由平台钱包中心作为唯一账务权威（`issuer + sub + settlementDomainId + currency`，六态流水，最小货币单位整数），本项目只维护项目积分（`projectId + businessOrganizationId + issuer + sub + pointType`）和项目业务余额，消费统一现金余额时以服务身份调用钱包中心并写回交易标识；Windows 以后通过共享核心和独立 UI 适配扩展。该方案符合趋势，但必须在完成上述验收门槛前保持“架构候选”，不宣称已经完成工程验证。

## 15. 模块化与低耦合架构审计

### 15.1 审计结论

**现有计划具备正确分层方向，但原状态尚未达到“代码必须低耦合”的可执行标准。** 主要问题不是模块数量不足，而是缺少强制的依赖方向、模块公开接口、跨模块事件契约和自动化架构测试。本章补齐后，架构可作为实现基线。

必须修正一个旧表述：不能把全部业务逻辑都固化在 ArkTS。ArkTS 负责鸿蒙 UI、Feature 状态和平台适配；需要跨 HarmonyOS、OpenHarmony、Windows 复用的 Fusion DOM、Command schema、格式解析、排版规则和渲染接口应进入跨端 Fusion Core 或平台无关契约层。

### 15.2 客户端模块边界

建议按“领域能力 + 端口适配”组织，不按页面堆目录：

```text
client/
├─ app-shell/                 # ArkUI 启动、路由、窗口、主题、断点
├─ features/
│  ├─ auth/                   # 登录状态机，只依赖 UserCenterPort
│  ├─ workspace/              # 工作区编排，不包含渲染算法
│  ├─ document/               # 文档用例、版本、保存
│  ├─ canvas/                 # 视口、选择框、输入映射
│  ├─ layers/                 # 图层面板投影与命令
│  ├─ properties/             # 属性面板 schema renderer
│  ├─ typography/             # 字体/段落/文本流用例
│  ├─ assets/                 # 素材、字体、色板、模板
│  ├─ ai-assistant/           # AI 计划、审批、Job 展示
│  ├─ export/                 # 导出预设和进度
│  └─ account/                # 用户、组织、钱包只读投影
├─ application/              # Use Case、CommandBus、QueryBus、事务边界
├─ contracts/                # DTO/Schema/Event；无 ArkUI、无数据库依赖
├─ platform-ports/           # 文件、网络、安全存储、浏览器、输入、窗口接口
├─ platform-ohos/            # HarmonyOS/OpenHarmony adapter
├─ engine-port/              # Fusion Core 的窄接口
└─ napi-adapter/             # NAPI/C ABI 绑定，不暴露 Skia 类型给上层
```

依赖方向固定为：

```text
app-shell / feature UI
        ↓
application use cases
        ↓
domain contracts + ports
        ↓
adapters（NAPI / HTTP / Casdoor / file / database）
```

下层不得反向引用上层；Feature 之间不得直接访问对方内部状态。跨 Feature 协作只能调用公开 Use Case、Query 或发布领域事件。

### 15.3 Fusion Core 模块边界

```text
fusion-core/
├─ document-model/     # Fusion DOM、稳定 ID、版本迁移
├─ command-core/       # Command、Transaction、Undo/Redo、回放
├─ vector-core/        # 路径、几何、布尔接口
├─ raster-core/        # 像素层、蒙版、非破坏调整描述
├─ text-layout/        # 文本流、样式、中文规则
├─ color-core/         # 色彩对象、ICC 引用、转换接口
├─ resource-core/      # 资源引用、哈希、去重
├─ render-graph/       # DOM → 中间渲染图，不直接绑定 UI
├─ format-spi/         # importer/exporter 插件接口
└─ platform-c-api/     # 稳定 C ABI，供 NAPI 与 Windows 调用
```

**严格禁止**：

- Fusion DOM 保存 `SkPath`、`SkBitmap`、ArkUI 对象、数据库行对象或 HTTP DTO。
- UI 直接调用 Skia、FreeType、PDFium、lcms2。
- 格式导入器直接修改画布状态；必须生成 Fusion DOM 或 Command batch。
- AI 模块直接写 DOM；必须生成可审批、可撤销的 Command Plan。
- NAPI 把第三方库类型暴露给 ArkTS；只暴露自有稳定结构与句柄。

### 15.4 Go 后端模块化单体

```text
server/internal/
├─ identity/          # Casdoor/OIDC adapter、Subject、会话上下文
├─ membership/        # 业务组织成员关系查询与当前组织上下文（调用独立成员关系服务）
├─ entitlement/       # 项目权益查询与策略
├─ project-points/    # 项目积分（HDS_CREDIT）账本与不可变流水
├─ business-balance/  # 项目业务余额（HDS_STORE）账本
├─ wallet-bridge/     # 调用平台钱包中心：held/captured/released/refunded/reversed
├─ document/          # 文档元数据、版本、ACL
├─ asset/             # 对象存储引用、上传和资源扫描
├─ command/           # 远程命令提交、幂等、审计、版本冲突
├─ job/               # 持久化状态机、排队、取消、重试
├─ ai/                # 模型协议 adapter、路由、预算，不写文档
├─ export/            # 导出用例，消费文档快照
├─ audit/             # 追加式审计接口
└─ platform/          # pgx、Redis、NATS、S3、OTel 实现
```

每个模块只允许导出 `api.go` / `ports.go` / `events.go` 中声明的公开契约；禁止其他模块导入其 `internal` 实现、数据库查询包或数据表结构。

后端允许的依赖：

```text
transport → application module API → domain → port
platform adapter → port
job worker → module application API
```

后端禁止的依赖：

- Handler 直接调用 `pgx/sqlc`。
- `document` 直接查 Casdoor 数据库或钱包数据表。
- `ai` 直接扣余额或修改文档；流程必须为 `reserve wallet → run job → command plan → approve/apply → settle/release`。
- `wallet` 依赖 AI、文档或 UI；它只识别可信 `product_id`、subject、organization、unit、transaction。
- NATS 事件作为同步事务的唯一依据；资金和文档版本以 PostgreSQL 事务状态为准。

### 15.5 模块通信规则

| 场景 | 机制 | 约束 |
|---|---|---|
| 模块内强一致写入 | Application service + PostgreSQL transaction | 一个事务只由一个领域模块拥有 |
| 跨模块同步查询 | Port / Query interface | 返回稳定 DTO，不返回 ORM/sqlc 类型 |
| 跨模块异步通知 | Versioned domain event | 至少一次投递，消费者幂等 |
| 客户端交互 | CommandBus / QueryBus | UI 不直接改 Store 或 DOM |
| 引擎调用 | EnginePort | 跨 NAPI 使用窄 DTO、句柄和明确内存所有权 |
| 外部 AI/MCP/CLI | Command/Job API | 与 GUI 共用 schema、权限、审计和版本检查 |

领域事件命名采用过去式并版本化，例如：

```text
identity.user-snapshot-updated.v1
wallet.credit-reserved.v1
job.completed.v1
document.command-applied.v1
asset.ingested.v1
```

事件只表达已发生事实，不携带密钥、完整文档、巨型二进制或第三方库对象。

### 15.6 公共契约与版本治理

必须建立唯一契约仓库：

```text
contracts/
├─ fusion-dom/*.schema.json
├─ commands/*.schema.json
├─ events/*.schema.json
├─ jobs/*.schema.json
├─ permissions/*.schema.json
├─ wallet/*.schema.json
├─ openapi/hds-api.yaml
└─ c-api/include/hds_core.h
```

- OpenAPI、CLI、MCP Tool、Skill 输入从同一 JSON Schema 生成或校验。
- Command、Event、Fusion DOM 和 C ABI 各自独立版本，禁止使用软件营销版本替代协议版本。
- 新字段默认可选；删除/重命名/改变语义必须提升主版本并提供迁移器。
- 所有 ID 使用稳定、不含业务含义的标识；显示名、邮箱、文件路径不作为跨模块主键。

### 15.7 依赖注入与配置

- 使用构造函数注入，不使用全局 Service Locator。
- Domain 不读取环境变量、系统属性或配置文件；配置在 composition root 解析后以只读 Options 注入 adapter。
- 时间、UUID、随机数、文件系统、网络和模型调用均通过 Port 注入，保证确定性测试。
- 禁止单例持有当前文档、当前用户或事务连接；会话状态显式绑定 workspace/request context。

### 15.8 自动化架构门禁

实现阶段必须把低耦合从“约定”变成 CI 门禁：

1. **依赖图门禁**：检测循环依赖、Feature 横向内部引用、domain 引用 adapter/UI/ArkUI/pgx。
2. **公开 API 门禁**：跨模块只允许访问声明的 public package；禁止深层路径导入。
3. **契约兼容门禁**：OpenAPI/JSON Schema/Event/C ABI 做 breaking-change 检测。
4. **替身测试**：Casdoor、钱包、模型、对象存储、NAPI 均可替换为 fake adapter，不启动真实基础设施也能测试 Use Case。
5. **命令一致性测试**：同一 Command 经 GUI/CLI/MCP 输入后产生相同 schema、权限判断和 DOM 结果。
6. **渲染隔离测试**：Fusion DOM 金样不含 Skia/ArkUI 类型；相同快照跨端输出落在容差阈值内。
7. **模块数据所有权测试**：禁止跨模块 SQL join 直接写入；跨域数据使用 ID/快照/事件。
8. **故障隔离测试**：Casdoor、AI、NATS、S3 任一不可用时，本地编辑和已打开文档仍可工作；钱包扣款不得形成半完成状态。

### 15.9 模块化验收标准

满足以下条件后，才能认定架构达到低耦合：

```text
- 任一 AI 模型供应商可替换，不修改 document/canvas 模块
- Casdoor adapter 可被 fake OIDC adapter 替换，不修改业务 Use Case
- Skia 可升级或增加 Windows backend，不修改 Fusion DOM schema
- CLI/MCP 可关闭或移除，不影响 GUI 核心编辑
- wallet/entitlement 可独立测试，不加载文档引擎
- 单个格式 importer 可作为插件增删，不改主文档模型
- Feature 模块不存在循环依赖和内部路径越界引用
- 所有跨模块写操作均经过 Command/Transaction/Audit
```

**审计结论**：按照本章约束实施后，系统属于“模块化单体后端 + 端口适配客户端 + 跨端 Fusion Core”的低耦合架构。模块不是微服务数量的同义词；首期保持单体部署，但代码边界、数据所有权和契约版本必须像可拆服务一样严格。
